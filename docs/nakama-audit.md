# Nakama integration audit — 2026-10-06

Scope: application-owned Godot transport/account/lobby/profile/leaderboard/battle/replay code, Go RPCs and match handlers, matchmaking, persistence, leaderboard reconciliation, and local deployment configuration. Visual animation code is presentation; it does not decide online results. This is a source and integration review, not a certification or load test.

## Corrections implemented

| Area | Correction |
|---|---|
| Session lifecycle | Cached sessions go through the SDK account API before opening a socket, enabling SDK token refresh and detecting invalidated tokens. Reconnect never authenticates a fresh device session automatically. |
| One active client | Existing Nakama `single_socket` and `single_session` policies retained. New socket presences replace older ones; delayed old leave events cannot evict the newer presence. |
| Leaderboards | HTTP-only reads no longer open another socket, which could otherwise disconnect the current socket under `single_socket`. |
| Commands after recovery | Command sequence belongs to the transport, observes server acknowledgements, and survives scene replacement. Server sequences reset on a new socket presence, but not a repeated join by the same presence. |
| Snapshot isolation | Ignore messages from other match IDs. |
| Socket ownership | Failed socket initialization closes the partially initialized socket. Closing HTTP-only connections marks them closed. Leaving the recovery lobby cancels recovery unless ownership is being handed to gameplay. |
| Recovery failures | HTTP authentication failures require explicit login. Known terminal realtime join failures end recovery; transient reconnect rejection/network failures retry. SDK realtime errors are WebSocket exceptions, distinct from HTTP status codes. |
| Matchmaking cleanup | Nakama session-end hook deletes only the queue entry belonging to that session. A new session may replace a stale entry immediately. Old cancellation/session-end events cannot erase a newer search. |
| Room directory | Replaced custom SQL lookup with server-owned Nakama Storage collection `riftbound_rooms`, read/write permissions 0/0. Create-only version `*` reserves codes and CAS updates publish match IDs. Cleanup is versioned and checks match ownership. Expired dead reservations can be reclaimed on collision. |
| Input validation | Room/queue RPC payloads limited to 16 KiB; action payloads retain existing 2 KiB limit. Validate decks before kicking an older room presence. |

## Existing behavior consistent with Nakama

- Device authentication uses a locally persisted random identity; concurrent editor instances have separate persistent slots/accounts. A guest identity needs an account-linking feature if cross-device recovery is later required.
- Authoritative Go matches validate sender session, action sequence, phase/round, deck and game actions. Client animation and local replay do not override online outcomes.
- Hidden enemy preparation information is removed from recipient snapshots.
- Matchmaker properties/rating ranges are replaced with server-owned values. Matched users explicitly join an authoritative match. Timeout bot assignment shares a lock with the matching callback to prevent double allocation.
- Leaderboards are authoritative. MMR permits decreases with SET; wins are reconciled from durable results. Client requests cannot directly award points.
- Gold used while preparing a round belongs to match state. Nakama Wallet is for persistent currencies; moving temporary round gold into Wallet would change the game semantics.
- Friends, Groups, Payments and Notifications are optional product features. Empty tabs do not indicate an incorrect integration. The screenshot's recovery-test account is generated by integration tests and does not run the normal display-name onboarding.

## Persistence choices and limits

Room data now uses Nakama Storage. Existing `rift_rooms` SQL tables are left untouched to preserve data, but no longer read/written by the runtime. Restarting the local server ends existing in-memory matches, so there is no active-match migration.

Custom application tables remain for battle results, per-match rewards and MMR. They use atomic SQL transactions, row locks and unique result ledgers to prevent duplicate rewards across retries. They do not edit Nakama internal tables. These are deliberate advanced-runtime exceptions to the recommendation to prefer built-in storage; converting them to separate ordinary storage writes would lose their multi-record transaction guarantee. Dashboard Storage does not show these custom tables. Leaderboards still use Nakama's API.

Active match state and the queue are in memory. A client disconnect is recoverable while the match exists; a server restart does not restore an active battle. SQL result persistence is synchronous in the match handler and needs latency/load measurement before increasing concurrency. The in-memory queue implementation assumes the current single-node deployment; distributed matchmaking requires a shared reservation design before enabling multiple Nakama nodes.

Local debug HTTP and known debug credentials remain local-development configuration. Public deployment requires HTTPS/WSS, production secrets, restricted console access and database backups. This audit does not claim production readiness.

The online gameplay test previously assumed an actor stays at its deployment position at the instant battle begins.
